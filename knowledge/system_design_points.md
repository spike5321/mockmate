# 系统设计题 解题框架与常见题目

> 本文件是 MockMate 演示用知识库语料，内容为公开技术常识汇总。

## 一、四步走框架

1. **澄清需求**（别急着画图）
   功能边界是什么？用户量级多大？读写比例如何？一致性要求到什么程度？
   能接受多大延迟？先问清楚再设计，这一步能刷掉大半的失分。
2. **容量估算**
   QPS、存储量、带宽的量级。口算即可，目的是让方案规模和题目量级匹配，
   不需要精确数字。
3. **设计核心链路**
   接口定义 → 数据模型 → 存储选型 → 核心流程串起来。
4. **扩展与权衡**
   缓存、分库分表、异步化、限流降级；以及每一步引入了什么新问题。

## 二、常见题目与核心考点

### 短链接系统

- **核心**：长链接 ↔ 短码的双向映射
- **短码生成**：发号器 + Base62 编码（把自增 ID 转成 62 进制字符串）
  也可以用哈希（如 MurmurHash）取前几位，但要处理碰撞
- **存储**：KV 结构，典型的读多写少，非常适合加缓存
- **跳转方式**：用 302 临时重定向，便于统计点击；301 会被浏览器长期缓存，
  之后就统计不到了
- **追问点**：如何防止短码被遍历？如何做自定义短码？

### 秒杀 / 抢购

- **核心矛盾**：瞬时高并发 + 库存绝对不能超卖
- **分层削峰**（从上到下依次过滤）：
  1. 前端：按钮置灰、答题、验证码，减少无效请求
  2. 网关：限流（令牌桶、漏桶），挡住超出容量的流量
  3. 服务层：库存预热到 Redis，用 **Lua 脚本**原子扣减，避免超卖
  4. 消息队列：异步下单，把瞬时峰值削平
  5. 数据库：最终落库，用唯一索引兜底防超卖
- **追问点**：Redis 扣减成功但下单失败怎么办？（对账 + 回补库存）
  如何防止同一个用户刷多单？（用户维度限购）

### 排行榜

- 用 Redis **ZSet**：score 存分数，member 存用户 ID
- `ZADD` 更新分数，`ZREVRANGE` 取 Top N，`ZRANK` 查某个用户的排名
- 追问点：数据量极大时如何分片？如何做"日榜/周榜/总榜"？（按时间维度拆 key）

### 分布式 ID

- **要求**：全局唯一、趋势递增、高可用、高性能
- **方案对比**：
  - 数据库自增：实现简单，但性能和可用性受单库限制
  - 号段模式：一次取一批 ID 缓存在内存，减少数据库压力
  - 雪花算法：时间戳 + 机器 ID + 序列号，趋势递增；
    缺点是依赖机器时钟，时钟回拨要处理

### 秒杀以外的常考题型

- 限流器设计（固定窗口、滑动窗口、令牌桶、漏桶的区别）
- 分布式锁（见 Redis 考点文件）
- 消息队列的重复消费与顺序消费
- 延时任务（时间轮、Redis ZSet、消息队列延时消息）

## 三、常被追问的权衡表

| 选择 | 优点 | 代价 |
|---|---|---|
| 加缓存 | 响应快、减轻数据库压力 | 一致性变复杂，要处理三大缓存问题 |
| 分库分表 | 突破单机存储与连接数上限 | 跨库 join 和事务变难，需要全局 ID |
| 消息队列异步 | 削峰、解耦、提高吞吐 | 复杂度上升，要处理重复消费和消息丢失 |
| 读写分离 | 分担读压力 | 主从延迟导致读到旧数据 |

## 四、回答时的常见失分点

- 只讲方案不讲理由，被问"为什么"就答不上来
- 不做容量估算，方案规模和题目量级不匹配（小系统上微服务、大系统上单机）
- 忽略失败路径：缓存挂了怎么办？消息丢了怎么办？上游超时怎么办？
- 完全不提监控、告警和灰度
- 只讲最终方案，不讲"我先考虑了 A，发现 B 问题，所以改成 C"的推导过程
