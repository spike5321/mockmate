# Redis 高频考点

> 本文件是 MockMate 演示用知识库语料，内容为公开技术常识汇总。

## 一、缓存三大问题

### 1. 缓存穿透

**现象**：查询一个数据库里也不存在的 key。缓存永远不命中，请求全部穿到数据库。
典型场景是恶意用不存在的 ID 刷接口。

**常用解法**：
- 缓存空值（key 不存在也缓存一个空标记，设较短的过期时间）
- 布隆过滤器：在缓存之前拦掉"一定不存在"的 key

### 2. 缓存击穿

**现象**：某个**热点 key** 过期的瞬间，大量并发请求同时打到数据库去重建缓存。

**常用解法**：
- 互斥锁：只让一个请求去重建缓存，其他请求短暂等待后重试
- 热点数据不设过期时间，由后台任务异步更新

### 3. 缓存雪崩

**现象**：大量 key 在**同一时刻集体过期**，或者 Redis 实例整体不可用，
数据库被瞬时流量打垮。

**常用解法**：
- 过期时间加随机抖动，避免同时失效
- 多级缓存（本地缓存 + Redis）
- 限流与降级，保住数据库

**三者的区别一句话说清**：穿透是"查不存在的"，击穿是"一个热点过期"，
雪崩是"一大批同时过期或整体挂掉"。

## 二、缓存与数据库的一致性

主流策略是 **Cache Aside**：先更新数据库，再**删除**缓存（而不是更新缓存）。

为什么删而不是更新？因为并发下两次更新缓存的顺序无法保证，
可能后写的旧值覆盖先写的新值，留下长期脏数据。删除操作则天然幂等。

即便如此，极端并发下仍有短暂不一致的窗口，所以关键业务会再加一层：

- **延时双删**：更新数据库后删一次缓存，短暂延迟后再删一次
- **订阅 binlog 异步刷新**：用 Canal 之类的工具订阅数据库变更，异步重建缓存

## 三、持久化

- **RDB**：按时间间隔生成数据快照。文件小、恢复快；缺点是可能丢失最后一次
  快照之后写入的数据，且 fork 时在大内存实例上会有明显停顿。
- **AOF**：记录每条写命令。可配置每秒刷盘，数据更安全；缺点是文件更大、恢复更慢。

生产环境通常两者同时开启，用 RDB 做快速恢复、AOF 保证数据完整度。

## 四、常用数据结构与典型场景

| 结构 | 典型场景 |
|---|---|
| String | 缓存对象、计数器（INCR）、分布式锁 |
| Hash | 存储对象的多个字段，可单独更新某个字段 |
| List | 简单消息队列、最新列表 |
| Set | 去重、共同好友（交集运算） |
| ZSet | 排行榜、延时队列（score 存时间戳） |

## 五、分布式锁

基本写法是 `SET key value NX PX 30000`，四个要点：

- **NX**：只有 key 不存在时才设置成功，保证互斥
- **PX**：必须设过期时间，否则持锁进程崩溃会导致死锁
- **value 用唯一值**（如 UUID）：释放锁时先校验是不是自己加的锁，避免误删别人的
- **释放锁用 Lua 脚本**：把"校验 + 删除"两步做成原子操作

更严格的场景可以用 Redlock（多实例加锁），但它对时钟漂移比较敏感，
业界对它的必要性有争议。单实例 + 唯一值 + Lua 释放，已经能覆盖大部分场景。

## 六、性能与容量常识

- Redis 单机 QPS 通常在万级到十万级区间，取决于命令复杂度和网络往返
- 单实例内存不宜过大，否则持久化 fork 和重启载入都会明显变慢
- **大 key**（单个 value 过大）和**热 key**（单个 key 访问过于集中）都要提前发现并拆分，
  否则会拖垮单个分片
- 集群模式下多 key 操作受限于同一 slot，设计 key 时可以用 hash tag 控制分布
