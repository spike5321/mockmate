# HTTP 与网络基础 高频考点

> 本文件是 MockMate 演示用知识库语料，内容为公开技术常识汇总。

## 一、状态码

| 类别 | 含义 | 常见 |
|---|---|---|
| 2xx | 成功 | 200 OK、201 Created、204 No Content |
| 3xx | 重定向 | 301 永久、302 临时、304 Not Modified |
| 4xx | 客户端错误 | 400 参数错、401 未认证、403 无权限、404 不存在、429 限流 |
| 5xx | 服务端错误 | 500 内部错误、502 网关错误、503 服务不可用、504 网关超时 |

面试常问的是 **401 与 403 的区别**（未认证 vs 已认证但无权限）、
**502 与 504 的区别**（上游返回错误 vs 上游没在超时时间内响应）。

## 二、HTTP 与 HTTPS

HTTPS = HTTP + TLS。TLS 握手大致过程：

1. 客户端发起连接，服务端返回证书（内含公钥）
2. 客户端校验证书链的有效性，生成一个对称密钥，用公钥加密后发给服务端
3. 双方之后都用这个对称密钥加密通信

**为什么最后用对称加密？** 非对称加密的计算开销大得多，只适合做密钥交换；
真正的数据传输用对称加密兼顾安全和性能。

## 三、GET 与 POST

- GET 语义是"读取"，应当幂等、可缓存，参数放在 URL
- POST 语义是"提交"，不幂等，参数放在 body

补充两点常被追问的：GET 请求也可以带 body（协议没禁止，但很多框架不支持，
不建议依赖）；URL 长度限制主要来自浏览器和服务器实现，不是 HTTP 协议规定。

## 四、TCP 三次握手与四次挥手

**三次握手**（建立连接）：

1. 客户端 → 服务端：SYN（我想连你）
2. 服务端 → 客户端：SYN + ACK（收到，我也连你）
3. 客户端 → 服务端：ACK（收到）

**为什么是三次？** 为了让双方都确认"我的发送能力"和"对方的接收能力"都正常，
并且同步双方的初始序列号。两次无法让服务端确认客户端收到了自己的 SYN，
四次则多余。

**四次挥手**（断开连接）：因为 TCP 是全双工的，一方说"我没数据要发了"（FIN），
不代表另一方也发完了，所以需要 FIN、ACK、FIN、ACK 四步。
主动关闭方最后会进入 TIME_WAIT 状态等待一段时间，确保对方收到最后的 ACK。

## 五、HTTP/1.1 与 HTTP/2

- HTTP/1.1 存在**队头阻塞**：同一连接上请求要排队，前一个慢会挡住后面的
- HTTP/2 引入**多路复用**：一个连接上并行传输多个请求/响应，
  另外还有头部压缩（HPACK）和服务端推送
- HTTP/2 仍然建立在 TCP 之上，所以 TCP 层的丢包仍会影响所有流；
  HTTP/3 改用 QUIC（基于 UDP）来解决这个问题

## 六、幂等性

幂等 = 同一个操作执行多次，结果和执行一次相同。对接口设计很关键：

- 查询、删除天然幂等（DELETE 不存在的数据仍是"已删除"状态）
- 支付、下单这类**必须靠幂等键**（业务唯一 ID）来保证重复请求不重复扣款
- 实现思路：把幂等键存到 Redis 或数据库唯一索引，重复请求直接返回上次结果
